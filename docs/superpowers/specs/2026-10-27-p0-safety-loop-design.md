# 第一阶段 P0：安全闭环最小兼容设计

- 日期：2026-10-27
- 状态：书面规格已获用户审阅通过；实施验证中
- 范围：classic 架构的跌倒触发、通知送达、未起床无应答升级、测试禁网

## 1. 目标

在不重写现有系统的前提下，修复以下会造成漏报或测试不可信的链路：

1. 老人跌倒后静止或姿态丢失时，跌倒候选不能仅因当前 `occupancy=False` 被吞掉。
2. 紧急消息只有在至少一个外部平台明确确认接收后，才视为外部送达。
3. 外部未送达时，不得开启“已报警”的 30 分钟跌倒静默。
4. 未起床语音无应答必须通知家人，并按首检、复查区分紧急程度。
5. 默认测试不得依赖真实 API Key 或发起真实云端调用。

## 2. 已确认的产品语义

### 2.1 未起床无应答分级

- 08:30 首检时，如果视觉无法判断且语音无应答：发送**普通跟进**通知，不进入紧急升级链。
- 09:00 复查时，如果仍判断在床且语音无应答：发送**紧急**通知。
- 普通回复和包含求助关键词的回复沿用现有行为。

### 2.2 外部送达定义

以下任一条件满足，才算 `delivered=True`：

- 钉钉返回 HTTP 成功且响应体 `errcode == 0`。
- 飞书返回 HTTP 成功且响应体 `code == 0`。
- 通用 Webhook 返回任意 2xx。

以下情况不算外部送达：

- 只写入 SQLite。
- 只发布到本地 WebSocket 控制台。
- 只创建了一个后台 HTTP 任务。
- HTTP 200 但平台响应体表示签名错误、参数错误或其他失败。
- 没有配置任何外部通知渠道。

多个渠道并存时，至少一个渠道明确成功即可令本次消息 `delivered=True`；其他渠道的失败仍须记录。

## 3. 方案选择与边界

采用**最小兼容方案**：保留现有 `notify.send()` 的旧返回契约，新增结构化回执接口，只让需要送达保证的安全场景等待回执。

不采用全量修改所有调用方返回类型，避免扩大回归面；不在本阶段引入持久化重试队列、新消息平台、Home Assistant 或 VLA 改造。

本阶段的重试是当前进程内的有限重试。进程崩溃后的消息恢复、独立外部看门狗和持久化队列属于后续部署工作，不在本次完成声明内。

## 4. 组件设计

### 4.1 跌倒候选触发

修改 `sensors/perception.py` 的 `sensor.sudden_still` 发布条件：

- 使用 `quiet_since` 对应的静止开始时刻。
- 通过 `occ.occupied(quiet_since)` 判断当时是否有人。
- `quiet_since is None` 时不得发布候选。
- 保留现有运动突变阈值和其他触发条件。

这样可以避免静止等待期间 occupancy 过期吞掉候选，同时保持“从未看到人形”的负样本不触发。

### 4.2 结构化通知回执

在 `skills/notify.py` 增加不可变结果对象，字段固定为：

```python
NotificationResult(
    msg_id: int | None,
    attempted: bool,
    delivered: bool,
    channels: dict[str, str],
)
```

约束：

- `msg_id` 仅表示本地消息落库结果。
- `attempted` 表示是否至少尝试了一个外部渠道。
- `delivered` 只由外部平台明确成功决定。
- `channels` 以渠道名映射到稳定结果标签，例如 `delivered`、`failed`、`not_configured`；不得包含 URL、Token、签名或完整响应体。
- 家人到老人的消息不执行外发，`attempted=False`、`delivered=False`。

新增回执式发送入口供跌倒场景使用；现有 `send()` 继续返回 `msg_id | None`，避免影响其他动作。

### 4.3 重试与失败记录

- 网络异常、HTTP 429、HTTP 5xx：每个渠道最多尝试 3 次，使用短指数退避。
- 其他 HTTP 4xx、平台业务错误、无法理解的 2xx 平台响应：立即停止该渠道重试并记录失败。
- 不同渠道并发派发，单渠道失败不得阻断其他渠道。
- 超时和重试参数写入 `config/settings.yaml` 的 `notify` 分区。
- 最终结果写入事件日志；全渠道失败时写 `notify_failed`，成功时写 `notify_delivered`。
- 日志只记录渠道名、结果标签、尝试次数和消息 ID，不记录敏感配置。

### 4.4 跌倒静默联动

`actions/fall.py` 的紧急路径改为等待结构化回执：

- `delivered=True`：开启现有 `re_alert_s` 静默。
- `delivered=False`：不开启静默，保留后续候选或手动触发再次报警的机会。
- 本地消息、语音询问和事件日志仍按现有路径执行。
- 返回值继续兼容现有场景 YAML 和测试。

### 4.5 未起床无应答

调整 `actions/wakeup.py` 的语音检查，使无应答也调用通知出口：

- 首检：`urgent=False`，返回现有 `no_reply` 末态。
- 复查：`urgent=True`，返回现有 `no_reply` 末态，随后清理本次升级链。
- 普通回复和求助回复行为不变。

### 4.6 测试禁网

在 `tests/conftest.py` 增加自动夹具：

- 在 `skills.vision._chat_sync` 和 `skills.llm._chat_sync` 的最底层网络边界阻断真实调用，默认抛出明确的“测试禁网”异常。
- 测试可用自己的 monkeypatch 覆盖这些边界或替换更高层接口。
- 清除测试环境中的真实 API Key，并令已有客户端单例不能复用真实凭据。
- 不拦截本地 ASGI 测试、SQLite、合成视频或假硬件。

## 5. 测试设计（TDD）

先新增或修改测试，确认旧实现按预期失败，再修改生产代码。

### 5.1 跌倒感知

- 突变前确认有人，静止后姿态丢失且当前 occupancy 过期：必须发布一次 `sensor.sudden_still`。
- 从未确认人形：不得发布候选。
- 现有小运动、静止锚点和普通静止行为保持通过。
- 修复不得通过单纯增大 `hold_s` 或增加常驻姿态推理次数实现。

### 5.2 通知与静默

- 钉钉 HTTP 200 + 非零 `errcode`：判定失败。
- 飞书 HTTP 200 + `code == 0`：判定成功。
- 网络失败：按配置重试，最终回执失败。
- 一个渠道失败、另一个成功：整体送达，失败渠道仍有记录。
- 未配置渠道：回执未尝试、未送达。
- 紧急通知未送达：跌倒静默保持关闭；明确送达后才开启。

### 5.3 未起床

- 首检无法判断且无应答：普通通知一次，不进入 pending。
- 复查仍在床且无应答：紧急通知一次，升级链结束。
- 现有普通回复、求助关键词和已离床行为保持通过。

### 5.4 禁网与回归

- 验证默认模型网络边界已被阻断。
- 运行完整 pytest；不得出现真实云端请求。
- 检查测试只产生临时测试产物，不修改生产配置。

## 6. 验收标准

1. 新增测试在旧实现上能复现对应缺陷，在修复后全部通过。
2. 完整测试套件通过，且模型网络边界默认关闭。
3. 外部平台明确失败时，不显示为送达，也不开启跌倒静默。
4. 首检和复查的无应答通知级别符合第 2.1 节。
5. 不改变现有场景 YAML 接口、普通通知调用方式及 VLA 代码路径。
6. 不声称本阶段已经解决持久化重试、远程双向聊天、真机标定、7×24 运维或实景识别准确率。
