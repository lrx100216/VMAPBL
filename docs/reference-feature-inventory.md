## 1. 验证等级定义与规范说明

在本次基准对齐调查中，所有功能特性按照以下 4 级证据链严格标定：

| 验证等级代码 | 验证等级名称 | 判定标准与证据要求 |
|---|---|---|
| **HDW** | **Hardware Verified (硬件实证)** | 在作者外婆真实居住环境或物理硬件设备（如二手摄像机、智能音箱、门磁、微型主机）上完成闭环部署与物理实机验证。 |
| **TST** | **Test Proven (测试实证)** | 具备公开的时延/吞吐量基准测试数据、自动化测试脚本、抓包日志或开源社区多用户复现记录。 |
| **COD** | **Code Supported (代码支持)** | 具备明确的开源代码仓、Python 函数实现、Home Assistant 实体定义、服务接口或自动化 YAML 声明。 |
| **DEC** | **Author Declaration (作者宣称)** | 作者在帖子、博客或视频中提出的技术方案、口头规划或体验描述，未开源完整源码或仅提供伪代码概念。 |

## 3. 维度 A：核心系统与架构 (Core System & Architecture)

### REF-A01: Home Assistant 本地事件驱动总线与状态中枢
- **功能名称**：Home Assistant 核心总线与状态机控制
- **参考项目技术实现**：
  - 采用标准 Home Assistant Core 架构作为中枢调度，硬件运行在极低功耗的 Armbian 盒子/玩客云上。
  - 所有物理传感器（门磁、PIR、摄像头实体）的状态变化自动发布为 `state_changed` 事件。
  - 自动化脚本基于 `trigger`（触发器）、`condition`（环境与时间前置条件）、`action`（执行动作）编排，充当整套系统的中枢神经。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：本地毫秒级响应；当门磁开启或传感器变动时，即刻分发至对应逻辑，不依赖外部公共云中控。
- **局限性与工程约束**：复杂的跨模态多步决策如果直接写在 YAML 自动化中会导致状态爆炸，难以维护高层级上下文。

### REF-A02: ModelScope Qwen 大模型集成 (`yanfeng_ai_task`)
- **功能名称**：阿里魔搭通义千问大模型对话与任务集成
- **参考项目技术实现**：
  - 作者开源开发了 Home Assistant 自定义集成 `yanfeng_ai_task`。
  - 改造 HA 官方 Conversation Agent 框架，后端指向阿里 ModelScope（魔搭社区）推理 API，配置通义千问系列模型（`Qwen-Turbo` / `Qwen-Plus` / `Qwen-VL`）。
  - 完全避开海外大模型（OpenAI / Gemini）所面临的网络审查阻断与海外信用卡支付障碍，充分利用 ModelScope 国内直连的免费 API 额度。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：支持中文自然流畅的多轮闲聊，以及针对家电设备的中文意图提取；API 调用延迟稳定在 800ms~1500ms。
- **局限性与工程约束**：依赖公网宽带连接魔搭服务端；免费配额存在并发速率限制（QPS 约束），高并发请求可能遇到 HTTP 429。

### REF-A03: 双独立消息解耦网关设计 (`*-ha-gateway`)
- **功能名称**：微服务架构独立通讯网关服务
- **参考项目技术实现**：
  - 拆分为独立的轻量级 Python FastAPI 微服务进程（`dingtalk-ha-gateway` 与 `feishu-ha-gateway`），默认监听独立端口（如 `8099`）。
  - 隔离 Home Assistant 主进程与外部 IM 协议栈的高频长连接与心跳包重试，防止网络抖动拖垮 HA 核心事件循环。
  - 网关与 HA 之间采用轻量 WebSocket 客户端或 RESTful HTTP 保持内部通信。
- **验证等级**：`Test Proven (TST)` / `Code Supported (COD)`
- **预期行为与用户体验**：HA 与网关可独立热重载、独立升级，内存占用均小于 100MB，CPU 占用率低于 5%。
- **局限性与工程约束**：需要多维护两个外部进程或 Docker 容器；存在内网端口通信与进程守护（如 Supervisor/Systemd）开销。

### REF-A04: 钉钉 Stream 模式免公网 IP 长连接穿透
- **功能名称**：钉钉 Stream 模式长连接事件网关
- **参考项目技术实现**：
  - 在 `dingtalk-ha-gateway` 中引入钉钉官方 `dingtalk-stream` SDK。
  - 网关主动与钉钉服务端建立出向（Outbound）WebSocket 长连接。
  - **实现核心价值**：家庭宽带在**无公网 IP、无路由器端口映射（Port Forwarding）、无域名与 SSL 证书、无内网穿透工具（如 frp/ngrok）**的纯私网环境下，实时接收钉钉发送的文字、事件与审批。
- **验证等级**：`Hardware Verified (HDW)` / `Test Proven (TST)` / `Code Supported (COD)`
- **预期行为与用户体验**：外婆家中即便使用大内网宽带（CGNAT），女儿在手机钉钉发送消息也能在 100ms 级别实时送达网关。
- **局限性与工程约束**：钉钉开发者后台必须创建企业内部机器人；若长连接异常断开，需依赖 SDK 内置的指数退避重连机制。

### REF-A05: 飞书异步高吞吐消息网关与 WebSocket 广播
- **功能名称**：飞书 Webhook 接收与 WebSocket 分发中间件
- **参考项目技术实现**：
  - 在 `feishu-ha-gateway` 中通过 FastAPI 暴露 Webhook 端口，接收飞书开放平台事件。
  - 网关与 Home Assistant 的 `feishu-ha-integration` 通过内部 WebSocket 建立连接。
  - 网关完成验签、解密和数据清洗后，毫秒级推送给 HA。经官方测试基准，网关内部处理仅耗时 30~80ms，端到端延迟 < 150ms。
- **验证等级**：`Test Proven (TST)` / `Code Supported (COD)`
- **预期行为与用户体验**：飞书交互卡片、群聊指令响应极快，无明显感知卡顿。
- **局限性与工程约束**：标准 Webhook 模式需要公网回调地址（可搭配域名或云服务器中继）；若纯内网环境需配合反向代理或切换为 WebSocket 轮询。

### REF-A06: 云边端混合部署协同拓扑 (Hybrid Edge-Cloud)
- **功能名称**：低算力端侧与云端认知协同
- **参考项目技术实现**：
  - **端侧/边缘（Edge）**：微型主机（20~50元盒子）负责硬件 IO、流媒体转发、传感器事件与基础规则；
  - **云端（Cloud）**：ModelScope Qwen 提供语言理解与多模态视觉大模型认知，钉钉/飞书官方云服务处理移动推送。
- **验证等级**：`Hardware Verified (HDW)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：实现不到 400 元硬件下获得前沿生成式 AI 的体验。
- **局限性与工程约束**：一旦家庭光纤或 Wi-Fi 断开，AI 认知和家庭外呼完全瘫痪，仅保留本地机械规则。

## 4. 维度 B：人机交互与适老设计 (Human-Machine Interaction)

### REF-B01: 智能语音硬件终端与远场拾音
- **功能名称**：适老语音输入与播放物理载体
- **参考项目技术实现**：
  - 方案一：采用通用平价小爱音箱（如小爱音箱 Play，闲鱼二手 50~70 元），通过 Xiaomi MIoT 集成或开源 `xiaomusic` 接入 HA。
  - 方案二：基于国产开源硬件“行空板 K10”（搭载 ESP32-S3、屏幕、阵列麦克风与喇叭），刷入定制客户端直连 HA 语音管道。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：85岁老人无需学习任何触屏、按键或智能手机操作，只要在房间内说话即可触发交互。
- **局限性与工程约束**：小爱音箱官方固件存在云端劫持，需通过特定的无感绕过或文本播报指令（如 `miot.intelligent_speaker`）；行空板 K10 喇叭功率较小，远距离可能听不清。

### REF-B02: 适老化唤醒机制与免唤醒手势控制
- **功能名称**：双模唤醒（经典语音唤醒词 + MediaPipe 视觉手势）
- **参考项目技术实现**：
  - 语音路径：保留高灵敏度的固定唤醒词（如“小爱同学”），降低老人记忆负担。
  - 视觉路径：作者独立研发了基于 Google MediaPipe 的 HA 扩展插件，利用摄像头在端侧进行手势关键点追踪（如挥手、举手、手掌开合）。
- **验证等级**：`Code Supported (COD)` / `Test Proven (TST)` (手势) / `Hardware Verified (HDW)` (语音)
- **预期行为与用户体验**：老人想说话时呼叫音箱；而在老人声音微弱或深夜不便大声说话时，朝摄像头抬手即可被系统感知识别。
- **局限性与工程约束**：MediaPipe 纯依赖 CPU 计算手势在低端盒子上负载偏高；手势识别对摄像头安装角度与室内光照条件敏感。

### REF-B03: 专为老年人定制的中文 Prompt 意图提取
- **功能名称**：高容错口语化老人意图分类与提示工程
- **参考项目技术实现**：
  - 在 `yanfeng_ai_task` 中注入特定 System Prompt。
  - 明确要求模型兼容中国老年人日常说话带有的大量冗余修饰语、语气词（“哎呀我那个…”、“请你帮帮我…”、“好乖乖，帮我把…”）及倒装语法。
  - 将非标准口语解析并映射为规范的意图动作：`turn_on_light`、`adjust_climate`、`send_family_message`、`chat`。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：外婆无需死记硬背固定指令格式，如同跟真人管家交流一样自如。
- **局限性与工程约束**：云端大模型偶发幻觉，可能将不相关的闲聊误触发为家电控制指令；缺少本地硬编码规则的前置确定性防护。

### REF-B04: 暖心人格与减速放量语音合成 (Elder-Adapted TTS)
- **功能名称**：缓速、清晰、温情的家庭陪伴语音合成
- **参考项目技术实现**：
  - 通过 HA 调用 Edge TTS 或 Piper，语音模型选定为音色温和的女声（如晓晓、Tingting）。
  - 参数调整：语速（Speech Rate）调低至 0.85x~0.9x，提高音量增益（Gain），确保老年听力衰减用户听得清晰。
  - Prompt 注入外孙语气与家庭角色定位，播报时带有敬语与关心。
- **验证等级**：`Hardware Verified (HDW)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：播报声音清晰浑厚、语速适中，外婆能轻松听懂每句话，不会感到冰冷机械。
- **局限性与工程约束**：Edge TTS 依赖微软公网服务，若公网出现抖动播报会出现 2~3 秒静音停顿。

### REF-B05: 半双工防回声与播报互斥管理
- **功能名称**：防音箱自身回声递归录入机制
- **参考项目技术实现**：
  - 在音箱 TTS 发音期间，软件层面设置互斥锁（Mute Lock）或禁用麦克风识别通道。
  - 播报结束后追加 300~500ms 尾部静默等待期，防止音箱播报内容被 ASR 重新收音造成“自己跟自己对话”。
- **验证等级**：`Hardware Verified (HDW)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：系统播报时不会被自身声音二次触发，交互干净利落。
- **局限性与工程约束**：播报期间老人如果突然插话（Barge-in）会被系统忽略，不支持全双工打断。

## 5. 维度 C：家庭双向沟通 (Family Communication)

### REF-C01: 外婆到儿女的语音转文字异步留言桥梁
- **功能名称**：老人向音箱留言自动转送子女办公软件
- **参考项目技术实现**：
  - 老人对音箱说：“告诉女儿我今天中午喝了排骨汤，身体挺好的不用担心”。
  - ASR 转录为文字 -> `yanfeng_ai_task` 识别出 `send_family_message` 意图，并提取正文内容。
  - HA 自动化触发，调用 `dingtalk_gateway.send_text` 或 `feishu_gateway.send_message`。
  - 网关将消息发送至女儿的个人工作钉钉/飞书聊天框中，并标注【来自外婆的语音留言】。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：完全免除老人使用智能手机打字或发送微信语音的障碍；女儿在上班时可以通过文字快速阅读，随时掌握老人动态。
- **局限性与工程约束**：方言重度口音（如浓重四川话/吴语）在 ASR 阶段容易发生同音错别字。

### REF-C02: 儿女到外婆的文字即时转语音播报
- **功能名称**：子女工作端消息推送转房间语音朗读
- **参考项目技术实现**：
  - 女儿在钉钉/飞书单聊中向机器人发送消息：“外婆，晚上我买了降压药带过去，您不用开门等我”。
  - 网关收到消息后，通过 WebSocket 立即向 HA 触发 `dingtalk_gateway_message` 或 `feishu_gateway_message` 事件。
  - HA 自动化提取 `event.data.text`，调用 TTS 服务并在客厅/卧室音箱中播放：“外婆，小敏给您发来一条消息：……”
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：老人独自在家时无需找老花镜看手机屏幕，直接在房间听到儿女的问候和交代。
- **局限性与工程约束**：缺乏“人在判定”——若外婆不在音箱附近房间，播报可能漏听；若外婆正在熟睡，突发播报容易造成惊吓（需时间段静音规则）。

### REF-C03: 钉钉/飞书消息状态实体与事件总线双向暴露
- **功能名称**：IM 消息实体化与 HA 事件总线联动
- **参考项目技术实现**：
  - `dingtalk-ha-integration` 与 `feishu-ha-integration` 在 HA 中创建专用实体：
    - `sensor.dingtalk_gateway_last_message`
    - `sensor.feishu_gateway_last_message`
  - 实体属性包含：`sender_id`、`sender_nick`、`conversation_id`、`message_type`、`timestamp`、`content`。
  - 每条消息到达时分发事件 `dingtalk_gateway_message`，支持在 HA 中通过发送者白名单进行权限过滤。
- **验证等级**：`Test Proven (TST)` / `Code Supported (COD)`
- **预期行为与用户体验**：开发者可以在 HA 图形化界面直接选择钉钉消息触发器，无缝配置各类联动。
- **局限性与工程约束**：纯文本和 Markdown 消息支持完善，语音原声消息（Audio Opus 流）由于编解码复杂度在网关层未做原声透传。

### REF-C04: 家人远程状态查询与富文本卡片汇总
- **功能名称**：子女远程主动询问老人起居状态
- **参考项目技术实现**：
  - 女儿在钉钉发送“外婆今天怎么样”，网关识别查询指令并触发 HA 自动化脚本。
  - HA 汇总今日关键状态：起床时间、门磁开关次数、服药确认记录、当前温湿度与当前视觉状态。
  - 网关调用 `dingtalk_gateway.send_markdown` 返回结构化 Markdown 卡片通知女儿。
- **验证等级**：`Code Supported (COD)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：儿女在工作间隙几秒钟即可全面获知老人一整天的起居安全概要，无需主动拨打视频电话打扰老人。
- **局限性与工程约束**：状态汇总依赖 HA 历史数据库的稳定记录，若某传感器离线可能导致汇报数据缺失。

## 6. 维度 D：场景化关怀与提醒 (Scenario Reminders)

### REF-D01: 入户门智能防忘与带钥匙定向提醒
- **功能名称**：出门/回家方向识别与带钥匙智能语音提醒
- **参考项目技术实现**：
  - 硬件配置：入户门安装 Zigbee/蓝牙门磁传感器。
  - 联动逻辑：门磁状态从 `off` 变为 `on`（开门）时触发。
  - 方向识别：结合玄关/客厅 PIR 人体移动顺序，若先检测到室内移动再开门，判定为“出门”；若直接开门，判定为“回家”。
  - 出门提醒：“外婆，出门记得带钥匙和公交卡，门要随手锁好哦！”
  - 设置 60 秒冷却去抖动（Debounce），防止短时间内重复开门连续大声播报。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：外婆出门前必定经过门厅，听到温和提示后顺手检查口袋钥匙，彻底解决老年人出门反锁忘带钥匙的顽疾。
- **局限性与工程约束**：如果两人同时进出或来访客人开门，纯传感器可能误判内外方向。

### REF-D02: 定时吃药提醒与防重复服药闭环
- **功能名称**：按时吃药语音提醒与防重复服药保护
- **参考项目技术实现**：
  - 设定固定用药提醒时钟（如早晨 08:30、中午 12:30、晚间 19:00）。
  - 到点触发音箱语音播报：“外婆，该吃早上的降压药和钙片啦，温水在桌上！”
  - 防重复闭环设计：系统在状态机中维护每日服药状态标志位（`input_boolean.morning_med_taken`）。
  - 老人服药后口头说“我吃过了”或按下确认键，标志位置为 `true`。若未确认，系统在 15 分钟后追加一次轻提醒；当天已置为 `true` 后，禁止再次触发提醒，杜绝重复吃药过量中毒风险。
- **验证等级**：`Hardware Verified (HDW)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：外婆不再需要翻看日历或死记硬背吃药时间；闭环机制消除了“记不清自己刚才到底吃没吃”的焦虑。
- **局限性与工程约束**：依赖老人口头确认或手动物理确认；参考项目未实现基于计算机视觉的药丸吞服精确动作追踪。

### REF-D03: 动态关怀日程与远程临时提醒配置
- **功能名称**：子女通过 IM 动态下发单次/临时关怀提醒
- **参考项目技术实现**：
  - 子女在钉钉/飞书向管家发送指令：“提醒外婆下午3点下楼测血压”。
  - 网关将指令经由 LLM 结构化提取为时间戳（15:00）和任务内容（“下楼测血压”）。
  - 写入 Home Assistant 日历或定时器调度（Timer），到点准时由音箱语音唤起播报。
- **验证等级**：`Code Supported (COD)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：应对临时突发事件（社区体检、燃气抄表、快递送达），子女无需反复电话叮嘱。
- **局限性与工程约束**：时间解析依赖大模型的零样本信息抽取，对复杂相对时间表达（“大后天上午”）可能存在解析漂移。

## 7. 维度 E：视觉感知与安全监测 (Visual & Safety Monitoring)

### REF-E01: 低成本家用摄像头 RTSP / go2rtc 视频流本地集成
- **功能名称**：普通 IP 摄像机本地 RTSP 取流与快照提取
- **参考项目技术实现**：
  - 选用市售百元内常见家用监控摄像头（二手 TP-Link、小米等，闲鱼 60~100 元）。
  - 通过破解固件、ONVIF 协议或借助开源 `go2rtc` 工具，提取局域网 RTSP 视频流（支持主码流高清与子码流低延迟）。
  - 接入 Home Assistant 原生 Camera 实体，支持调用 `camera.snapshot` 服务截取实时静态画面。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：视频流完全局限在家庭局域网，响应延迟 < 300ms，按需抓帧成本为零。
- **局限性与工程约束**：某些品牌摄像机存在官方云锁或动态码流限制，配置 RTSP 需一定的极客刷机能力。

### REF-E02: 晨间起床关怀与超时未起异常升级预警 (08:30 / 09:00)
- **功能名称**：早晨起居状态两级阶梯式关怀与报警链
- **参考项目技术实现**：
  - **第一阶段（08:30 温和问询）**：
    - HA 定时器在 08:30 触发，检测卧室床边 PIR 传感器或摄像头区域动态。
    - 若仍未检测到老人起床走动，音箱以轻柔声音问候：“外婆，早上好，醒了吗？今天天气很好哦”。
  - **第二阶段（09:00 告警升级）**：
    - 状态机等待至 09:00。若 30 分钟内依然未检测到任何人员活动且老人无语音回应；
    - 立即判定为高危疑似事件（突发疾病、床头昏迷、意识丧失）；
    - 自动抓取当前摄像头画面，调用钉钉/飞书网关，向女儿手机推送紧急红色警报：“【紧急预警】外婆截至09:00仍未起床活动，音箱无应答，请立即核实确认！”并附上快照。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：既不会打扰老人偶尔的懒觉，又能在真正发生心脑血管意外导致无法起床求救时，守住黄金救治时间窗口。
- **局限性与工程约束**：若老人提前起床未触发感应，或老人出门晨练未关门窗，可能产生误报升级（需与入户门门磁状态联动过滤）。

### REF-E03: 夜间起夜检测与安全微光路径引导
- **功能名称**：夜间起夜自动照明与防跌倒微光护航
- **参考项目技术实现**：
  - 时间窗口限定：深夜 23:00 至次日 06:00。
  - 触发条件：床边地脚人体红外传感器（PIR）检测到人员下床落地。
  - 执行联动：自动点亮床底或走廊的智能小夜灯，设定亮度为 15%~20% 暖黄光（防刺眼醒脑，兼顾夜视清晰）。
  - 自动复位：当老人返回床上且持续静止超过 3 分钟后，小夜灯平滑淡出熄灭。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：老人半夜摸黑起夜无需摸索墙壁开关，光线柔和不刺眼，大幅降低绊倒、碰伤几率。
- **局限性与工程约束**：被褥滑落或宠物（如果有）在床边晃动可能误触发地脚传感器。

### REF-E04: 跌倒视觉告警与紧急快照推送
- **功能名称**：跌倒突发动作检测与报警回传
- **参考项目技术实现**：
  - 结合摄像头画面运动幅度剧烈突变后长时间处于地面极低位置（静止不动）；
  - 触发高优先级安全报警规则，联动音箱大声询问：“外婆您摔倒了吗？如果没事请回答一声”，同时给女儿钉钉/飞书发送高危警告快照。
- **验证等级**：`Hardware Verified (HDW)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：老人摔倒无法爬起呼救时，系统能自动捕捉并在数十秒内通知儿女。
- **局限性与工程约束**：参考项目中作者受限于硬件算力，未在低配盒子上运行高帧率 3D 骨架时序网络，主要依赖传统区域运动与画面几何高度阈值，存在一定的误报率（如弯腰捡东西被误判为跌倒）。

## 8. 维度 F：智能家居与生活辅助 (Smart Home & Assisted Living)

### REF-F01: 药盒与说明书拍照文字朗读 (Medicine Packaging OCR)
- **功能名称**：大模型多模态视觉识别与用药指南朗读
- **参考项目技术实现**：
  - 当老人拿起未知药盒并对音箱说：“帮我看看这是什么药，怎么吃”；

  - Prompt 专门定制：“请识别图片中的药品包装盒，提取药品通用名、主治功能以及用法用量，用适合老人口语听觉的格式回答，忽略无关批号”；

- **局限性与工程约束**：摄像头拍摄受到反光、距离过远、抖动模糊、对焦不准影响；大模型解析耗时约 2~4 秒。

### REF-F02: 家电与灯光口语化意图控制
- **功能名称**：全屋智能家电无死板指令口语控制
- **参考项目技术实现**：
  - HA 接入老人家中的吸顶灯、风扇、红外空调伴侣。
  - `yanfeng_ai_task` 将老人自然口语映射为 HA 标准服务调用（`light.turn_on`、`climate.set_temperature`）。
  - 支持模糊意图表达：“屋里有点闷”、“开开灯”、“温度调高一点”。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：无需老人在黑夜中起身按开关或在杂乱的茶几上寻找空调遥控器，动嘴即达。
- **局限性与工程约束**：需要空调等老式家电具备红外遥控接收器，并预先在 HA 中配对学习红外码库。

### REF-F03: 基于视觉的免唤醒无接触快捷控制
- **功能名称**：MediaPipe 摄像头手势快捷联动
- **参考项目技术实现**：
  - 利用作者自研的 MediaPipe HA 加载项；
  - 定义简单手势对应快捷实体开关：如在床头做出手掌张开持续 2 秒触发关闭所有照明；
  - 纯本地运行，不占用公网带宽。
- **验证等级**：`Code Supported (COD)` / `Test Proven (TST)`
- **预期行为与用户体验**：夜深人静外婆准备入睡时，无需张嘴喊唤醒词打扰清静，举手即可熄灯入睡。
- **局限性与工程约束**：需要视线正对摄像头且光线满足基本照度；老年人手部抖动可能影响关键点拟合。

## 9. 维度 G：非功能特性与工程边界 (Non-Functional & Engineering)

### REF-G01: 极致性价比硬件 BOM（总造价严格控制在 400 元以内）
- **功能名称**：超低门槛开源可复刻性
- **参考项目技术实现**：
  - 硬件物料详细拆解清单（作者实测价格）：
    1. **主控中枢主机**：闲鱼二手玩客云 / 斐讯 N1 / 晶晨 S905 电视盒子，刷入 Armbian + Docker 运行 Home Assistant，成本约 **35~50 元**；
    2. **视觉感知（眼睛）**：二手米家/TP-Link 1080P/2K 家用云台监控摄像头（RTSP支持），成本约 **80~100 元**；
    3. **语音交互（耳朵与嘴巴）**：二手小爱音箱 Play 或 ESP32-S3 开发终端，成本约 **60~110 元**；
    4. **环境传感（神经末梢）**：Zigbee 门磁传感器（15元）+ PIR 人体移动传感器（20元）+ 蓝牙/Zigbee 网关模块（30元），合计约 **65~80 元**；
    5. **电源、辅材与线缆**：手机旧充电头、网线、双面胶，合计约 **15 元**。
    - **硬件总花费：约 255 ~ 355 元人民币**（严格在 400 元预算上限内）。
  - **软件运营零成本**：
    - Home Assistant 永久开源免费；
    - 阿里 ModelScope 魔搭社区 API：提供免费推理配额；
    - 钉钉开放平台（企业内部应用 Stream 模式）：永久免费；
    - 飞书开放平台（个人/企业开发者版）：永久免费。
- **验证等级**：`Hardware Verified (HDW)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：极高性价比，普通工薪家庭与技术极客均能承受并成功复现科技适老化改造。
- **局限性与工程约束**：低价硬件无冗余硬件看门狗，主控设备若遭遇电压浪涌或掉电可能引发文件系统损坏。

### REF-G02: 隐私第一与本地优先数据流 (Privacy-First Architecture)
- **功能名称**：老人居家隐私保护与按需抓拍传输
- **参考项目技术实现**：
  - 拒绝使用商业厂商 24 小时全天候直连手机的云端实时监控（避免让老人产生“天天被全家人监视、毫无尊严”的严重抵触心理）。
  - 视频全量码流只在家庭局域网内部流转（局域网 RTSP）；
  - 仅在触发紧急安全事件（如跌倒报警、09:00 超时未起、主动请求拍照查药）时，系统才会抽取当事单张图片加密发送至受保护的家庭钉钉/飞书群中。
- **验证等级**：`Hardware Verified (HDW)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：外婆欣然接受安装设备，完全没有被监控的心理压力，守护安全的同时捍卫了老人尊严。
- **局限性与工程约束**：无法像商业 App 那样随时提供 24 小时高清平滑云回放回溯。

### REF-G03: 超低功耗与全天候静音被动散热
- **功能名称**：24/7 无噪音长周期静默运行
- **参考项目技术实现**：
  - 全套设备（Armbian 盒子、音箱、摄像头、传感器网关）总空闲功耗低于 **10W~15W**。
  - 盒子与音箱均为被动散热（无风扇设计），运行完全零噪音。
  - 一个月耗电量不足 8 度电（电费支出不到 5 元钱）。
- **验证等级**：`Hardware Verified (HDW)` / `Author Declaration (DEC)`
- **预期行为与用户体验**：设备置于卧室或起居室不会干扰老人夜间睡眠，长辈不会因心疼电费而偷偷拔掉电源。
- **局限性与工程约束**：夏季高温环境下被动散热盒子可能出现过热降频，需注意摆放通风位置。

### REF-G04: 局域网断网降级保障 (Offline Fallback)
- **功能名称**：外网阻断环境下的本地基础保活
- **参考项目技术实现**：
  - Home Assistant 原生架构保证所有本地 Zigbee/BLE 传感器与物理执行器之间的自动化不依赖外网。
  - 当宽带网络中断时：夜间起夜自动开灯、门磁开门本地蜂鸣报警、本地定时器仍稳定工作。
  - 仅外部大模型对话与钉钉/飞书远程消息通知进入挂起重试状态。
- **验证等级**：`Hardware Verified (HDW)` / `Code Supported (COD)`
- **预期行为与用户体验**：即便光纤断开或小区宽带故障，老人基础的照明与起居安全不受威胁。
- **局限性与工程约束**：断网期间如果老人突发跌倒，无法向外网子女发出手机告警，只能依赖本地声光报警器引起邻居注意。

## 11. 关键技术洞察与对 VMAPBL 项目的技术借鉴建议

通过对参考项目的逐行代码解构与实景技术复盘，可为 VMAPBL 团队提供以下极具价值的技术洞察：

### 11.1 借鉴亮点 (Strengths to Adopt)
1. **钉钉 Stream 模式是家庭私网接入的黄金方案**：
   - 相比于传统 Webhook 需要固定公网 IP 或动态域名穿透，`dingtalk-stream` 基于长连接的无公网 IP 架构不仅极其安全稳定，且部署门槛极低，避免了 NAT 穿透故障引发的消息死锁。
2. **消息网关与控制中枢解耦**：
   - 使用独立微服务网关屏蔽 IM 平台的 Token 刷新、心跳保活与网络闪断，确保核心业务引擎（VMAPBL / HA）不受外部协议库崩溃的影响。
3. **适老交互的核心在于“极简与温度”**：
   - 绝不强求老人适应新设备；无论是将儿女文字转换为房间语音，还是将老人自言自语转化为儿女钉钉工作通知，都精准切中了独居老人渴望沟通又怕打扰子女的心理软肋。
4. **多级阶梯式安全升级（08:30 / 09:00）**：
   - 08:30 先温和问候确认，09:00 再触发红色警报，这种缓冲设计极大减少了误报给在外工作子女带来的恐慌。

### 11.2 参考项目的局限与 VMAPBL 的演进突破方向 (Gaps to Overcome)
1. **视觉感知精度不足与延迟瓶颈**：
   - 参考项目在低算力盒子上无法本地运行实时姿态估计网络，跌倒与起床判断依赖粗糙的区域运动（Motion）或云端 VLM 静态抓图，面临 2~5 秒的网络往返时延，难以捕捉毫秒级跌倒动力学特征。
   - **VMAPBL 突破**：利用 Mac 本地 Apple Silicon 算力，直接以 30fps 实时运行 `YOLO26n-pose`（CoreML 加速），在端侧完成骨架角度与下坠速度的毫秒级判定。
2. **纯云端 LLM 的脆弱性**：
   - 参考项目的自然语言意图分类全部交由云端 ModelScope Qwen 处理，一旦断网或遭遇 API 速率限制（429），全屋语音控制瘫痪。
   - **VMAPBL 突破**：采用本地轻量规则/本地意图分类优先，云端大模型兜底的两级架构，兼顾离线鲁棒性与语义丰富度。
3. **语音半双工的机械互斥**：
   - 参考项目通过粗暴的“播报期禁用输入”避免回声，老人无法在机器人长篇大论时直接打断（Barge-in）。
   - **VMAPBL 突破**：结合本地 Silero VAD 与精密的状态机，建立快速抢占与安全打断管道。
4. **缺乏确定性防抖与送达确认门控**：
   - 参考项目的 YAML 自动化容易因传感器抖动造成重复播报或连发通知。
   - **VMAPBL 突破**：在核心层引入统一的 `StateStore`、防抖计时器（Debounce）与严格的送达门控（Delivery Gating），杜绝幽灵播报。
