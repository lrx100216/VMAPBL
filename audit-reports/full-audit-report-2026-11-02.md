# Part A：Executive Summary（首席技术官评估摘要）

### 1. 项目总体状态
VMAPBL（运行在 MacBook Air M2 上的本地 AI 养老管家）在**单点算法集成、本地端侧边缘推理（CoreML YOLO-pose / Apple Vision OCR / MOG2 运动滞回）以及严格的加载期 DSL 校验**上表现出了明显高于常规个人/原型项目的工程自觉。代码风格严谨，对历史安全漏洞（如命令注入、跌倒姿态丢失自锁、TTS 尾静默死锁等）进行了有针对性的补丁加固。

然而，从**专业级、生产级（Industrial / Medical-Grade Safety Critical System）**的养老守护标准来审视，该项目目前仍属于**高完成度的工程原型系统（High-Fidelity Engineering Prototype）**，**尚未达到可无人值守交付给独居老人家中实际运行的生产标准**。

### 2. 当前最值得肯定的工程实践
1. **TTS 与 Shell 交互零命令注入面**：`skills/tts.py` 使用 `create_subprocess_exec` 配合 `--` 分隔参数列表，且在单元测试中钉死了参数位置，彻底杜绝了外部文本输入导致的命令注入风险。
2. **场景引擎加载期确定性校验**：`core/scene_engine.py` 在启动期对所有 YAML 场景文件进行严格语法、字段白名单、`cooldown` 合法性（排斥 bool 与 NaN）、`choose` 嵌套深度（上限 8 层）的静态拦截，防止配置隐患留到运行时。
3. **MOG2 滞回闸门与姿态节流设计**：`sensors/perception.py` 采用 MOG2（30fps 低功耗）+ Pose（0.5s 节流）双级过滤，大幅降低了 M2 芯片无风扇环境下的发热与 CPU 占用。
4. **紧急通知持久化 Outbox 与平台回执闭环**：`skills/notify.py` 与 `core/log.py` 实现了紧急通知外发前持久化、有界退避重试（上限 8 次）以及钉钉/飞书平台业务级回执校验（排斥 HTTP 200 假成功）。
5. **安全关键词否定前缀护栏**：在 `fall.py` 与 `core/vla_agent.py` 中实现了 `_distress_in_reply` / `_distress_in_speech`，有效解决了“我没摔”因包含子串“摔”而导致误报紧急警报的常见语义缺陷。

### 3. 最严重的五个系统级问题
1. **【死亡重试锁定探针】`notification_outbox` 失败记录导致 `/readyz` 永久 503 且触发看门狗周期性外部骚扰（AUDIT-001）**：一旦外部通知彻底失败转为 `dead`，系统无任何接口或机制清理该记录，就绪检查锁定为 `False` 长达 30 天，看门狗每 30 分钟持续告警。
2. **【状态零持久化】核心看护事实全部为进程内内存态，崩溃重启引发重复用药报警与防护失效（AUDIT-003）**：每日服药打卡、定时去重、跌倒 30 分钟静默期、升级链进度均未存入 SQLite，一旦进程随 launchd 或系统睡眠重启，守护状态全部丢失。
3. **【业务逻辑跨天穿透】仪表盘时间线与起床时间未校验日期，昨日事件污染今日结论（AUDIT-002）**：`_wake_info` 盲读数据库最近记录，老人今日尚未起床时前端却展示昨日起床时间，向家属提供虚假的平安信息。
4. **【生产预检旁路裸奔】双击启动器与 LaunchAgent 默认未开启生产检查，服务端与 Webhook 处于零鉴权状态（AUDIT-004）**：未传入 `--require-production` 时，Token 与签名检查默认静默放行，任何人均可向本地端口推送伪造语音与跌倒警报。
5. **【关键业务链虚假完成】场景3（出门钥匙）与场景4（智能吃药）主视觉通道实际处于不可用状态（AUDIT-005）**：`settings.yaml` 缺失 `door_outside` 导致出门判定恒为 unknown；`models/pillbox.pt` 权重文件完全不存在，吃药检测永久处于降级语音状态。

### 4. 最大的系统性风险
**“双模架构（Classic 级联管线 vs VLA 极低功耗快慢分层）分裂带来的安全与成本失控”**。
VLA 模式将 Sentinel 哨兵捕获的每一次常规运动变化直接派发给云端多模态大模型，彻底丧失了 Classic 模式的低延迟（<50ms）与零成本（¥0）优势，变成了严重依赖外网与付费 Token 的脆弱管线；同时 VLA 绕过了状态触发器接线，导致多个场景在 VLA 模式下静默失效。

### 5. 是否适合当前预期用途？是否具备进入生产环境的条件？
- **当前用途评估**：适合作为开发者本地联调、家庭环境技术演示（Demo / PoC）及多模态养老概念验证。
- **生产准入裁决**：🔴 **禁止进入生产环境（No-Go for Production）**。在解决跨重启状态持久化、探针死锁、主路径权重补齐与严格鉴权之前，绝对不可交付给无人在场的真实老人家庭环境。

### 6. 下一阶段最重要的工作
将分散在各模块中的内存状态统一收敛至 SQLite 持久化层；修复 `/readyz` 对 `dead` 状态的管理缺口；强制所有启动方式绑定生产预检；补齐缺失的真实检测权重与 ROI 标定。

# Part C：完整问题清单（按严重程度排序）

### Issue ID：AUDIT-001
- **问题标题：** 外部通知死亡重试导致就绪探针 (/readyz) 与独立看门狗告警永久死锁
- **严重程度：** Critical
- **问题类型：** 可靠性 / 架构设计
- **文件路径与行号：** `core/health.py:42-53`, `core/log.py:274-282, 323-330`, `tools/healthcheck.py:35-40`
- **证据：** 
  `core/health.py:45-46` 明确断言：`checks["notify"] = (health["pending_count"] == 0 and health["dead_count"] == 0)`。
  实测运行 Python 脚本注入 8 次失败通知，通知状态转为 `dead`，`readiness()` 返回 `ready=False`。由于全项目没有任何清除、归档或重试 `dead` 记录的 API/UI，`log.prune_history(keep_days=30)` 默认保留 30 天，系统将在接下来的 30 天内持续返回 503，独立看门狗每 30 分钟向家属发送一次外部报警。
- **问题描述：** 紧急通知设计了最大 8 次重试后转 `dead`，初衷是防止重试风暴，但健康就绪检查却将 `dead_count == 0` 作为硬性门槛，形成“通知彻底失败 → 系统永久不就绪 → 独立看门狗持续刷屏报警”的自锁闭环。
- **触发条件：** 任何一次跌倒紧急通知由于外网彻底断开、Webhook Token 失效或平台连续返回 4xx 达到 8 次。
- **潜在影响：** 系统健康检查永久红牌，家属被看门狗报警骚扰长达一个月，最终被迫手动删除数据库或彻底停用看门狗。
- **验证状态：** 已复现
- **根本原因：** 将历史业务失败事实（审计用）与当前系统健康探测（存活/就绪用）混为一谈，缺乏对失败状态的“人工确认/已读消除（Acknowledge）”机制。
- **修复建议：** 
  1. `/readyz` 仅断言 `pending_count` 是否积压，移除 `dead_count == 0` 硬约束；
  2. 在控制台增加“通知失败历史与一键确认重试”接口（`POST /api/notifications/ack`）。
- **修复优先级：** P0
- **预计修复难度：** 低
- **修复后验证方法：** 注入一条 `dead` 记录，断言 `/readyz` 返回 200，同时调用确认接口后 `dead_count` 清零。

### Issue ID：AUDIT-002
- **问题标题：** 仪表盘起床信息缺乏日期过滤，昨日数据泄漏为今日健康结论
- **严重程度：** High
- **问题类型：** 功能逻辑 / 数据准确性
- **文件路径与行号：** `server/dashboard.py:46-55`
- **证据：**
  ```python
  def _wake_info(log) -> tuple[float | None, str | None]:
      for event in log.recent(scene_id="wake_up", limit=50):
          ...
          if result.get("phase") == "first" and result.get("verdict") == "out_of_bed":
              return float(event["ts"]), "events:wake_up/out_of_bed"
  ```
  实测向数据库写入一条 36 小时前（昨天）的 `out_of_bed` 事件，调用 `_wake_info(log)` 仍然返回该时间戳，导致今天清晨仪表盘直接显示“已起床”。
- **问题描述：** 家人端只读摘要接口在计算老人起床时间时，仅按 `scene_id="wake_up"` 倒序取最新一条判定，未检查该事件的时间戳是否属于今天。
- **触发条件：** 每日 00:00 至次日 08:30（今日首检执行前）。
- **潜在影响：** 极高风险假阴性。老人如果夜间突发疾病未能起床，家属在早上 7:00 打开控制台时，看到的却是“已起床（显示昨天时间）”，产生致命误导。
- **验证状态：** 已复现
- **根本原因：** 时间序列事件聚合时缺少基于当天自然日（`datetime.now().date()`）的日期范围限定。
- **修复建议：** 增加时间戳检查：`if datetime.fromtimestamp(event["ts"]).date() != datetime.now().date(): return None, None`。
- **修复优先级：** P0
- **预计修复难度：** 低
- **修复后验证方法：** 在测试中注入前一天的起床事件，断言 `dashboard_summary` 的 `wake_time` 为 `None`，UI 呈现“未确认”。

### Issue ID：AUDIT-003
- **问题标题：** 关键守护状态零跨重启持久化，守护进程重启后产生重复骚扰与告警失效
- **严重程度：** Critical
- **问题类型：** 系统架构 / 可靠性
- **文件路径与行号：** `core/state.py:18-27`, `core/scene_engine.py:387-399`, `actions/medication.py:38, 58-67`, `actions/wakeup.py:25`, `core/vla_agent.py:94-117`
- **证据：**
  - `SceneEngine._time_fired`（定时触发去重字典）为类成员 `dict`；
  - `StateStore.medication_taken` 构造时硬编码初始化为 `False`；
  - `actions/wakeup._pending` 为模块级全局变量 `{"date": None}`；
  - `core/vla_agent._silence_until` 为浮点数模块全局变量。
- **问题描述：** 系统中所有跨时段的决策状态全在 Python 进程内存中。macOS 发生系统升级、LaunchAgent 重启、网络断线重启守护或人为重启后，当日守护记忆全部清空。
- **触发条件：** 主进程在白天发生任意一次崩溃、被 launchd 重启或用户重启机器。
- **潜在影响：**
  1. 老人若已于 09:35 服药，10:00 进程重启后，10:01 会再次触发并大声播报催促吃药；
  2. 若刚刚发生跌倒报警，武装了 30 分钟静默，进程重启后静默标志瞬间清零，可能因老人地上的翻动再次狂发紧急通知；
  3. 起床升级链首检状态丢失，09:00 复查被当成首检。
- **验证状态：** 静态充分 / 代码直接证明
- **根本原因：** 将“状态存储（StateStore）”设计为了纯内存单例，缺少持久化 backing store 及启动时的 Hydration（状态水化）机制。
- **修复建议：** 在 `butler.db` 中建立 `daily_state (date, key, value)` 表，状态更新同步落库，启动时恢复当天的状态。
- **修复优先级：** P0
- **预计修复难度：** 中
- **修复后验证方法：** 模拟设置状态后重启 `SceneEngine` 与模块，断言当日服药与静默标志依然有效。

- **根本原因：** 同步阻塞 C 库缺乏底层超时控制（RTSP `stimeout` / `timeout` 选项未注入）。

- **问题描述：** 手动触发场景接口在捕获异常后，将未脱敏的异常堆栈细节直接拼入 HTTP 响应返回给调用方。如果异常包含本地文件系统的绝对路径（例如视频文件路径、数据库锁定信息），会导致内部敏感信息泄露。
- **触发条件：** 手动触发一个执行出错的场景。
- **潜在影响：** 攻击者可通过错误回显探测本地系统文件结构与内部模块实现细节。
- **验证状态：** 静态证据充分
- **根本原因：** 采用快速开发时期的直接回显模式，未引入统一的对外安全错误脱敏层。
- **修复建议：** 对外仅返回通用错误提示和事件追踪 ID，详细异常堆栈写入 `logs/butler.log`。
- **修复优先级：** P3
- **预计修复难度：** 低
- **修复后验证方法：** 触发异常场景，验证 HTTP 响应中不包含绝对路径或系统敏感参数。

# Part E：改进路线图（四阶段演进计划）

### Phase 1：立即修复（上线阻断项 / P0，预计 1.5 人日）
*目标：消灭导致系统死锁、虚假安全信息与服务崩溃的致命缺陷。*
1. **解除死亡重试就绪探针死锁**（AUDIT-001）：修改 `core/health.py`，移除 `dead_count == 0` 的硬拦截，新增 `POST /api/notifications/ack` 清理接口。
2. **修复仪表盘起床时间跨天泄漏**（AUDIT-002）：在 `server/dashboard.py` 中强制增加自然日匹配，过滤昨日事件。
3. **建立核心看护事实 SQLite 持久化**（AUDIT-003）：在 `butler.db` 中建立 `daily_state` 表，使服药打卡、定时去重、跌倒静默和升级链进度支持进程重启自愈。
4. **强制启动器与部署文件绑定生产预检**（AUDIT-004）：在 `VMAPBL Butler.app` 与 `com.local.butler.guardian.plist.template` 中强制加入 `--require-production`，杜绝未鉴权裸奔。

### Phase 2：短期优化（技术债务与安全加固 / P1，预计 3 人日）
*目标：修补安全漏洞，补齐关键业务链缺失资产。*
1. **修复规则渲染存储型 XSS**（AUDIT-006）：在 `server/static/index.html` 中补齐 `escapeHtml` 转义。
2. **补齐门外 ROI 默认标定与通用药盒检测**（AUDIT-005）：补齐 `settings.yaml` 的 `door_outside` 多边形，解决场景3主路径哑火；固化基础药盒识别逻辑。
3. **加固大模型提示词防注入与播报清洗**（AUDIT-007）：使用 `<data>` 标签包裹 OCR 外部输入，并在 TTS 播报前增加合规前缀，阻断恶意欺诈指令。
4. **重构真实 Token 成本核算**（AUDIT-008）：废弃固定 ¥0.0008 单价，依据 API 实际返回的 tokens 和配置单价精确计算。

### Phase 3：架构改进（模块解耦与并发健壮性 / P2，预计 5 人日）
*目标：收敛架构分裂，增强硬件容灾能力。*
1. **统一双模架构事件流向**（AUDIT-010）：收敛 VLA 模式，将端到端决策限制在夜间突变或特定高风险场景，避免日常无意义调用云端大模型；补齐状态接线。
2. **增强摄像头异步生命周期管理**（AUDIT-009）：注入底层 RTSP 超时参数，防止 OpenCV 原生 `read()` 永久阻塞守护线程，确保网络抖动可自愈。
3. **构建硬件级 Hermetic 离线测试集**（AUDIT-012）：录制真实的 1 秒合成音频与低分辨率视频切片，让 Whisper 和 YOLO 推理真正接入集成测试，降低虚假置信度。
4. **将 `tools/` 依赖从生产服务端解耦**（AUDIT-011）：将 ROI 标定算法下沉至 `actions/`。

### Phase 4：长期演进（生产就绪与常驻稳定性 / P3，预计 10 人日）
*目标：达到医疗级/安全级长期稳定运行标准。*
1. **配置分层治理**（AUDIT-013）：将只读配置（代码库托管）与运行时动态标定数据（存放在 `data/`）分离，彻底消除工作树 Dirty 隐患。
2. **统一异常对外脱敏网关**（AUDIT-014）：建立全局 API 异常拦截器，禁止内部文件路径向外暴露。
3. **72 小时无泄漏稳压演练（Soak Testing）**：在正式交付老人家中前，使用实际硬件持续运行 72 小时，监控内存 RSS、文件句柄及 CoreML 内存泄漏情况。

# Part G：审计盲区与局限性说明

为了维持客观严格的工程纪律，本次审计明确声明以下审计盲区与客观限制：

1. **真实硬件外设未物理联调**：当前审计环境为沙箱运行环境，未接入真实物理网络摄像头（RTSP 设备当前 IP 不可达）、未插入真实外置麦克风硬件，麦克风与摄像头实际推流表现基于代码逻辑分析及本地回放路径验证。
2. **付费大模型 API 未真机放量调用**：为遵守“审计阶段禁止未经许可调用外部付费 API”的纪律，测试全过程保持网络隔离（`_block_cloud_network`），未向 DeepSeek 线上服务器发送大量生产测试请求。
3. **长期稳压（Soak Test）未达 72 小时**：本次审计基于全套测试用例（34.5s）和代码静态审查，未在当前环境下挂载连续 72 小时以上的超长实景稳压压力测试，超长期的 CoreML / CTranslate2 原生 C++ 扩展内存泄漏风险未能穷尽测量。
4. **macOS TCC 权限弹窗机制受宿主限制**：由于当前代码分析环境运行于无头/非交互终端，无法触发真实 macOS 本地窗口的相机/麦克风系统授权弹窗，关于权限获取的结论主要依据 `tools/permission_check.py` 的源码逻辑。
